## Technical foundations

**Already working:** production HTTPS, a www-to-apex 301, trailing-slash redirects, real HTTP 404 responses, static HTML content, English language metadata, descriptive titles, OG/Twitter cards, favicon/PWA assets, and crawlable internal links. The live query-string URL already served the built homepage canonical correctly; a canonical defect was not reproduced on production.

**Fixed:**

- Replaced the fragile source canonical calculation with a shared production URL helper using the configured site and normalized pathname. Query strings, fragments and preview hosts do not determine canonicals. OG URLs use the same canonical.
- Made Astro's trailing-slash policy explicit to match served routes and internal links.
- Kept the sitemap generated from the route data, with 27 canonical, indexable URLs. Removed build-generated `lastmod` values and unnecessary priority/change-frequency hints. Modification dates should be restored only if editorial dates are tracked accurately. [Google sitemap guidance](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap)
- Added Worker response headers excluding all `.pages.dev` preview hosts, the `/r/` utility and 404s from indexing. Production remains indexable. Both production and preview canonicals point to the public apex.
- Removed the robots exclusions for `/r` and `/404` so crawlers can read their noindex instructions; these static utility pages are excluded from the sitemap. Noindex requires crawl access. This is an indexing control, not an access-control mechanism. [Google robots and noindex documentation](https://developers.google.com/search/docs/crawling-indexing/robots-meta-tag)
- Added build verification to the existing frontend deployment workflow, covering sitemap membership, canonical/OG consistency, one H1, unique titles, parseable JSON-LD, internal links, redirects and preview/utility indexing headers.

Canonicals and redirects help Google consolidate duplicate URLs; they do not guarantee Google's selected canonical or a ranking increase. [Google canonical guidance](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls)

## On-page and content fixes

The homepage title and H1 now identify temporary email directly. Added a server-rendered section describing the product, three usage steps, timer/deletion behavior, suitable one-time tasks, receive-only limits, recovery risk, and the distinction from forwarding aliases. Native expandable answers cover common user questions. The inbox remains the primary functionality at the top of the page.

The 23 existing platform URLs remain stable. Removed unsupported claims about exact delivery times, sender subjects, blocklist severity, platform privacy practices, and success after a specific number of address regenerations. Changed the directory and popular links to describe guidance and restrictions rather than verified integration support. Added visible breadcrumbs on platform pages, and used the related-link component already present to preserve navigation between guides.

Material corrections include:

- **GitHub:** official documentation explicitly says disposable email services cannot be verified. The page now explains this restriction and points to GitHub's noreply approach for commit privacy. [GitHub email reference](https://docs.github.com/en/account-and-profile/reference/email-addresses-reference)
- **Discord:** email can be only one part of verification; phone and server requirements also apply. Removed the claimed guaranteed flow, VPN suggestion and unsubstantiated advertising assertions. [Discord verification documentation](https://support.discord.com/hc/en-us/articles/6181726888215-How-to-Verify-Your-Discord-Account)
- **Telegram:** a temporary inbox cannot replace the connected phone number. [Telegram FAQ](https://telegram.org/faq)
- **ChatGPT:** ongoing access to the account email matters. The guide no longer promises successful disposable signup or a guessed magic-link arrival time. [OpenAI login troubleshooting](https://help.openai.com/en/articles/7426629-why-cant-i-log-in-to-chatgpt)
- **YouTube/Gemini:** Google's verification of a non-Google email is distinguished from creating a Gmail inbox. [Google Account verification](https://support.google.com/accounts/answer/63950)
- **Finance and lasting accounts:** guidance recommends lasting email for payment records, subscriptions, purchases, workspaces and recovery. These are product-use recommendations, not claims that a platform accepts our domain.

Other compatibility labels explicitly say acceptance is unverified. Official documentation about a platform's verification process is not a successful signup test. The FAQs now explain that copying a password does not ensure later access and a regenerated address may use the same domain. Terms wording was corrected to match those facts. Removed the static sample Discord message from the hidden email reader and excluded the live address/reader from search snippets.

The intent is to improve accuracy and usefulness. The existence of templated pages alone does not prove a Google penalty; no manual-action evidence was available. These changes follow Google's guidance to provide original value and avoid unsupported or scaled low-value content. [Helpful content guidance](https://developers.google.com/search/docs/fundamentals/creating-helpful-content), [spam policies](https://developers.google.com/search/docs/essentials/spam-policies)
